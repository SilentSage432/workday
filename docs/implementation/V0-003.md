# V0-003 — quiet Capture and the Work schedule

Date: 2026-10-02.

The signed-in surface no longer keeps the whole Capture form open. The user can also record a personal Work schedule and the time zone that interprets it. This is not NOW, and it does not project Work cadence.

## Phone evidence

The deployed application was used on a phone. Resume worked and sat first, which is what V0-002 intended. The Capture form stayed expanded, so it occupied the screen and competed with that thread. The dark background stayed appropriate. The schedule for today's Work was still missing.

## Quiet Capture

Capture stays an interaction. The signed-in page shows **+ Capture** until the user opens it. The opened form asks "What needs doing?" The title and Save are the short path. Context, Planned, Due, and Must do stay behind **More options**.

Close hides the form. If the draft has a title, a Context, a planned day, a due date, or Must do, that draft stays in the signed-in view until a successful save, a sign-out, or a refresh. It is not written to Supabase. A failed save keeps the draft and leaves Capture open. A successful save clears the draft, closes Capture, and leaves the Active Thread as it was.

Resume stays above Capture. Opening the Work schedule and coming back does not throw the draft away, because that state lives with the signed-in view.

## Work schedule

A Work schedule entry is the user's own scheduled Work for one civil date. It is not a store schedule, a Task, a Block, or a Commitment.

`temporal_settings` holds one confirmed IANA time zone per user, and the instant they confirmed it. The phone may suggest `Intl.DateTimeFormat().resolvedOptions().timeZone`. Nothing is stored until the user saves that zone. Later correction is a Change control on the Work schedule surface. There is no profile, avatar, theme, or notification setting.

`work_schedule_days` holds at most one row per user per civil date:

| Column | Type | Null | Notes |
| --- | --- | --- | --- |
| user_id | uuid | no | Owner. Part of the primary key. |
| work_on | date | no | Civil date. Part of the primary key. |
| day_state | text | no | `off` or `scheduled` |
| start_local | time | yes | Local start. Null when Off. |
| end_local | time | yes | Local end. Null when Off. |
| shift_type | text | yes | `opening`, `mid`, or `closing`. Null when Off. |

No row means no schedule has been entered. Off is a row. Those are different.

Shift type is the user's choice. Opening, Mid, and Closing are not inferred from the clock, and they are not applied to Family, TeamLab, or Financial.

If `end_local` is earlier than or equal to `start_local`, the shift continues into the next civil date. The times stay as entered. The projection treats the interval as half-open: during includes the start and excludes the end. A local time that does not occur in the zone is not silently moved. An ambiguous repeated hour uses the first zone conversion that round-trips.

The week on screen is the Lowe's Work fiscal week, Saturday through Friday, from `workFiscalWeekStart` and the confirmed zone. Moving to the previous or next week adds seven civil days. That week is not applied outside Work. The screen reads the current instant at the application boundary and passes it into the projection. The projection does not call the clock.

`projectWorkDay` returns unknown, Off, or a scheduled shift with before, during, or after. The schedule surface shows that position for today. It does not rank Tasks, and it does not name cadence steps.

## Persistence and row level security

`persistence/workSchedule.ts` loads and saves the time zone, loads a date range, saves one day, and deletes one day. Components do not query these tables themselves. Selects omit `user_id`.

Row level security is on for both tables. `authenticated` may select, insert, update, and delete only its own rows. There is no `anon` policy.

## Live validation

`supabase/migrations/20261002234500_work_schedule.sql` was applied to the dedicated project `workday` (`ksmhgaamyheyhefbyglb`). Migration history is `context_and_task`, `active_thread`, and `work_schedule`.

Before the check, the real account had one Task and one Active Thread. The check used two temporary users inside one transaction and ended with `VALIDATION_PASSED_ROLLED_BACK`. It did not delete or update that Task or thread.

It checked that a new user has no zone and no schedule; a confirmed zone can be stored; a second row for the same date is rejected; an edit replaces the shift; Off stores null times and no shift type; a date with no row stays absent; an end earlier than the start is stored as entered; deleting a row returns that date to unknown; a scheduled row without a type is rejected; Off with a start time is rejected; another authenticated user cannot read, update, delete, or insert the zone or the schedule.

After the rollback: 1 user, 4 Contexts, 1 Task, 1 Active Thread, 0 time zones, 0 schedule rows.

## Browser

The signed-in Capture and schedule controls were not clicked in a browser. The provisioned password is not in this session. The sign-in screen remains the dark baseline.

## Exclusions

NOW, `rankNow`, Work cadence, Power Hour behavior, FSR behavior, opening and closing sequences, weekly obligations, Notes, Blocks, Commitments, Timeline, recurrence, reminders, Pulse, Google Calendar, notifications, voice, a service worker, and AI were not added.

## Observations

- Save sits under the title. More options sits under Save, and the optional fields appear above Save once opened, so the short path does not have to pass through them.
- An unsaved draft survives a trip to the Work schedule and back. It does not survive a refresh.
- Today on the schedule surface is the only place this tranche shows before, during, or after. Home still orients with Resume.
- Public sign-up on the hosted project was still not changed.
