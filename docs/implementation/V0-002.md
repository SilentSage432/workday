# V0-002 — Active Thread and Resume

Date: 2026-10-02.

The signed-in person can say what they are doing, leave that thread, or finish it, and still see it when they come back. This answers "What was I doing?" It is not NOW. Later composition authority includes the Active Thread as one independent truth beside Current Temporal Orientation. This slice still does not implement that composition, and it still does not infer a thread. See [../decisions/2026-10-04-present-moment-orientation.md](../decisions/2026-10-04-present-moment-orientation.md).

## Active Thread

An Active Thread is the user's current explicit thread of intention. In this slice it references one open Task.

The user establishes it with Start on that Task. The system does not infer it. Capture does not establish it. MUST DO does not establish it. A planned day does not establish it. A due date does not establish it. Time passing, an interruption, a Context, a refresh, and closing the browser do not clear it.

It remains until the user:

- completes the referenced Task
- starts a different open Task
- leaves the thread

Leaving the thread does not complete the Task. Starting a different Task does not complete the previous one. The product does not ask why, and it does not call either one a failure.

There is one current thread per user. V0 does not keep a suspended thread for another Context.

## Persistence

`public.active_threads` has one row per user:

| Column | Type | Null | Notes |
| --- | --- | --- | --- |
| user_id | uuid | no | Primary key. Owner. |
| task_id | uuid | no | Referenced Task |
| established_at | timestamptz | no | Instant the user established this thread |

`user_id` references `auth.users` and deletes the thread when the account is deleted.

`tasks` gained `unique (id, user_id)` so the thread can reference both columns. The foreign key is `(task_id, user_id)` to `tasks(id, user_id)`, with `on delete cascade`. Deleting the Task removes the thread. Completing the Task does not delete the Task.

A before trigger, `active_thread_requires_open_task`, rejects a thread whose Task is missing, owned by someone else, or already completed. The foreign key rejects a cross-owner reference even if that trigger were absent.

Row level security is enabled. The `authenticated` role may select, insert, update, and delete only its own row. Insert and update check the new row. There is no policy for `anon`.

The domain type is `ActiveThread`: `taskId` and `establishedAt`. It has no `user_id`. Row mapping lives in `persistence/activeThread.ts`.

Operations:

- `loadActiveThread`
- `establishActiveThread`
- `clearActiveThread`

`completeTask` is unchanged. It writes the completion instant. The screen does not issue a second delete.

## Completion consistency

When `tasks.completed_at` changes from null to an instant, `tasks_clear_active_thread_on_completion` deletes the owner's thread row if it references that Task. The trigger runs in the same transaction as the update. A committed completion cannot leave a durable pointer to that Task.

The Task row remains, including its completion instant, planned day, due date, and MUST DO flag.

The screen drops the local thread only after `completeTask` resolves. `projectResume` also returns nothing if the referenced Task is not in the open list.

## Resume

Resume is `projectResume` in `projections/resume.ts`. It takes the Active Thread and the open Tasks. It returns the referenced open Task and the establishment instant, or nothing.

It does not read Supabase, the system clock, or the network. It does not rank. It does not implement NOW or `rankNow`.

The establishment instant is stored and passed through. The screen does not show it as elapsed time.

## Establish, change, and clear

Start writes an upsert on `user_id`. If a thread already exists, the same row now references the newly chosen open Task and a new establishment instant. The previous Task stays in the open list.

Leave thread deletes the row. Both Tasks, if two were involved, stay open.

Creating a Task only calls `createTask`.

## Failure

The screen changes the thread, the open list, or Resume only after the corresponding write resolves.

If Start fails, the previous thread stays, and the failure says the current thread is unchanged when one existed.

If Leave thread fails, Resume stays, and the failure says the thread is still active.

If Complete fails, the Task stays open. If that Task was the thread, the failure also says the thread is still active.

## Mobile interaction

Resume is the first block on the signed-in page, above capture, so a returning phone does not have to pass the capture form to see it. The capture field takes focus only when there is no thread.

Resume shows the Task title, the line "This is what you're doing.", the same factual metadata as the list, Complete, and Leave thread. Those controls are full width and at least 48px tall.

Each other open Task has Start and Complete side by side. The current Task says "Current thread" instead of offering Start again. There is no swipe and no drag.

## Visual baseline

The page background is stone-950 (`#0c0a09`), with stone-100 text and stone-900 fields. `color-scheme: dark` is set so native controls follow. The manifest background and theme color match that background. This is a low-glare baseline for the existing screen, not a visual system and not a brand.

## Live validation

The migration `supabase/migrations/20261002223000_active_thread.sql` is the canonical schema change. It was applied to the dedicated project `workday` (`ksmhgaamyheyhefbyglb`).

Before the check, the dedicated project had one user, four Contexts, no Tasks, and no Active Thread.

Validation ran as one database transaction. It created two temporary users, exercised the steps below, and ended by raising `VALIDATION_PASSED_ROLLED_BACK`, which aborted the transaction. Afterward the project again had one user, four Contexts, no Tasks, and no Active Thread.

It checked:

1. A user can have no Active Thread.
2. That user can have two open Tasks.
3. Establishing Task A stores that thread.
4. Resume resolves to Task A while both Tasks are open.
5. Changing the thread to Task B leaves Task A open.
6. Task B is then the only thread.
7. Clearing the thread leaves both Tasks open.
8. Establishing Task A again, then completing it, removes the thread and keeps Task A stored with a completion instant.
9. Task B stays open.
10. A thread referencing another user's Task is rejected.
11. Under row level security, the other user cannot read or change the thread.

A second insert for the same user was rejected by the primary key. With the open-task trigger turned off inside that same transaction, the foreign key still rejected a cross-owner Task. With the trigger on, a completed Task was rejected. As the other authenticated user, select, update, and delete saw nothing, and an insert of the owner's thread was rejected by row level security. Completing the referenced Task as its owner, under row level security, cleared the thread and kept the Task row.

## Exclusions

NOW, `rankNow`, attention ranking, inferred urgency, recommendation ordering, and current-Context inference were not added.

Notes, Blocks, Commitments, Timeline, Work schedule UI, Work cadence UI, recurring obligations, reminders, Pulse, Google Calendar, notifications, voice, a service worker, and AI were not added.

## Observations

- Start is the visible word for establishing the thread. Leave thread is the visible word for clearing it without completing the Task. Clear remains the internal name.
- The completion trigger is the durable consistency mechanism. The projection is a second check, not the one that deletes the row.
- Public sign-up on the hosted project was still not changed in this tranche.
- Whether several Contexts should each retain a suspended thread remains open. This schema cannot store that.
- The signed-in Resume controls were not clicked in a browser. The provisioned password is not in this session. The sign-in screen was checked at a 390px width: the background is `#0c0a09`, there is no registration control, an empty submit stayed on that screen, and the page did not scroll sideways.
