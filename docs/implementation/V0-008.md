# V0-008 — Commitments

Date: 2026-10-02.

A Commitment is time constrained by something the user has committed to. This tranche stores that truth, records that the row was created here, and gives the smallest way to add, inspect, edit, and remove it.

Protected Time remains: "I have made this time unavailable for allocation."

A Block remains: "I have chosen what this time is for."

A Commitment means: "This time is constrained by something I have committed to."

## Storage

`commitments` is its own table. It is not Protected Time, a Block, a Task, a Work shift, or a generic event.

The title is required, trimmed, and at most 80 characters. The user writes it. The application does not invent it, and it is not a category.

There is no Context column. A Commitment such as "Dentist" does not need one. There is no Task id and no join to Tasks.

An all-day row stores the civil date and null clock times. A timed row stores local start and end on that date. The confirmed zone on `temporal_settings` interprets those times. It is not copied onto the row, so a later confirmed-zone change reinterprets existing local times. This tranche does not store a zone per Commitment, and it does not solve how an external calendar's zone would be kept.

If the end is earlier than or equal to the start, the Commitment continues into the next civil date. It does not cover further days.

`origin` is `user_created` for every row this tranche can store. The check constraint allows only that value. The title does not imply the origin. No Google event id, calendar id, sync token, or etag is stored. No external row is invented.

Saving a Commitment does not write Protected Time, a Block, a Task, Today, the Work schedule, or the Active Thread. Removing a Commitment removes only that row. Overlap with another Commitment, a Block, Protected Time, a Work shift, or a Task planned today is allowed and is not treated as a conflict. Nothing recurs.

## Authority

This application may edit and remove these rows because it is their source. A later external temporal source, such as Google Calendar, may supply a Commitment and keep authority over that fact. What this application may then edit, delete, or only observe is not decided. No synchronization, OAuth, or write-back is implemented.

## Time zone

A timed Commitment is not saved from a browser guess. Without a confirmed zone, Schedule says so and does not open the form. The existing confirmation control remains the path.

## Projection

`projectCommitments` takes stored Commitments, a supplied instant, and the confirmed zone. It does not read Protected Time, Blocks, the Work schedule, Tasks, a clock, the network, or the database.

An all-day Commitment is current on its civil date. A timed Commitment is current from its start until, and not including, its end. The Schedule list shows current, upcoming, and unresolved rows in civil order. Past rows stay stored and are not shown. The order is chronological, not a rank.

When a stored local time does not occur in the confirmed zone, the projection does not invent an instant and does not call the row current or upcoming. If the civil date is still today or yesterday, the row stays on the list as unresolved and the surface does not say the current time is inside it. If the civil date is already before yesterday, the row is past and stays off the list, because a timed interval cannot remain open beyond the next civil date. An ambiguous repeated local time keeps the stored clock text and uses the existing first round-trip instant.

The list does not calculate capacity, free time, a conflict, or a Timeline.

## Schedule

Commitments sit under Blocks on `/schedule`. The bottom bar is still Tasks and Schedule. Add commitment stays closed until opened. The form asks for a date, all day or timed, start and end when timed, and a title. Start and end reuse the 12-hour selects. Edit uses the same fields. Remove asks once on the row: "Remove this commitment?"

An open form that has not been saved is local. Cancel drops it. Leaving Schedule drops it. Protected Time and Block drafts are unchanged.

Work, Protected Time, and Blocks remain on the page as separate sections. That stack is temporary scaffolding. The later Schedule direction is one temporal canvas composed from these distinct facts. A later interaction may let the user select a period and say what that time means. Neither is built here.

## Left alone

Task, Today, Must Do, Due, Active Thread, Resume, Work schedule, Protected Time, Blocks, and the confirmed time zone are unchanged. No Task column changed.

Google Calendar, Gemini, OAuth, synchronization, Timeline, temporal composition, capacity, availability, Task and Commitment associations, recurring Commitments, recurring obligations, NOW, `rankNow`, Task ranking, Notes, reminders, Pulse, notifications, voice, a watch app, a service worker, AI, LLMs, machine learning, agents, a temporal canvas, and a visual redesign were not added.
