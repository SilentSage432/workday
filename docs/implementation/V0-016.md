# V0-016 — Current temporal orientation

Date: 2026-10-03.

Baseline: `133002383058b3c8042236cc477e2397e2d62a78` on `main` (V0-015, phone accepted).

NOW-CONTRACT-001 later names the first present-moment composition as this reading together with the Active Thread. This slice does not implement that composition. The projection still does not read the thread. Empty still means only that no established temporal fact contains the instant. See [../decisions/2026-10-04-present-moment-orientation.md](../decisions/2026-10-04-present-moment-orientation.md).

## Evidence carried forward

Active Thread is already explicit current intention. It is persisted, started by the user, and still there after a reload. Resume is that thread while the Task is open.

Established temporal facts already say what is true about time: a Work shift, Protected Time, a Block, and a Commitment. Their current/upcoming classifiers already exist. Schedule already draws them.

Those two answers did not meet. LIVE starts by composing them without collapsing them.

## What this adds

`projectCurrentTemporalOrientation` in `projections/currentTemporalOrientation.ts` takes an injected instant, the confirmed IANA zone, and the Work schedule, Protected Time, Blocks, and Commitments the caller already loaded. It returns the facts that contain that instant.

Protected Time, Blocks, and Commitments use `classifyProtectedTime`, `classifyBlock`, and `classifyCommitment`. Only a `current` result is included. An unresolved local time is not treated as containing the instant.

Work uses `projectWorkOrientation`. The fact is included only when that reading's schedule is `during`. Off, unknown, before, and after contribute nothing. If yesterday's overnight shift and today's shift both contain the instant, the later shift is the one Work orientation already selects. That is the existing Work rule, not a ranking against other kinds.

Every other matching fact is kept. A Block that starts earlier than the shift is listed by its start, not behind Work. When the date, all-day flag, and local start match, the tie-break is the Timeline source sequence: `work_schedule`, `protected_time`, `block`, `commitment`, then source id. That order is presentation support. It is not importance.

An empty `facts` array means no established truth contains the instant. The screen says "Nothing established contains this time." It does not say free, available, open, unscheduled, or unallocated.

The projection does not read Tasks, Must Do, due dates, Today, or the Active Thread. Calling it does not write a thread or a Block.

## Tasks

On `/`, Resume stays first. `CurrentTime` follows it. Work orientation follows that, unchanged: shift position, Power Hour, the next Work boundary, and the FSR sentence.

The temporal list names each fact:

- Work, the shift label, and the range
- Protected, the label when one exists, and the range
- Block, the purpose, and the range
- Commitment, the title, and the range

All day stays "All day." A range that continues into the next civil date says so. There is no warning when the Block's purpose and the Active Thread's title differ.

Without a confirmed zone, the section asks for one and links to Schedule, the same pattern as Today. It does not use the browser zone. If the zone cannot be loaded, it says so. If established time or the Work window cannot be loaded, it shows that failure instead of an empty reading.

Schedule is unchanged. The Active Thread is not shown there.

## Clock

The projection does not call `Date.now` or `new Date`. `TaskLoop` holds the instant. It replaces that instant at the next minute boundary, then arms the following minute. Stored bounds are local minutes, so the screen does not tick every second. When the page becomes visible again, it takes a fresh instant immediately, because a backgrounded timer may have been delayed. If the confirmed civil date changed, it reloads the previous-and-current Work window and the temporal rows. Overnight facts that are already loaded are reclassified from the new instant without waiting for that reload.

## Unchanged

No schema or migration. No Timeline change. No Active Thread persistence change. No Task edit, delete, reopen, sort, or drag. No Note, reminder, voice, or notification. No `/now` route. Work orientation still owns FSR, Power Hour, and the next shift boundary.

## Phone acceptance

On the phone, after this build is deployed:

A. Open Tasks with a confirmed time zone. Resume, when a thread exists, is still the first reading.

B. This time is directly under Resume. Work is still under that, with the shift and Power Hour behavior already accepted.

C. Create a Block whose range contains now, with a purpose that is not the Active Thread title. Start a different Task.

D. Tasks shows the Block under This time and the Task under Resume. There is no warning that they differ.

E. If the shift also contains now, Work appears in This time as well as in the Work reading. Both stay.

F. Leave the thread. The Block remains under This time. The Task stays open.

G. Reload. The thread and the Block are both still there.

H. Remove or wait out every fact that contains now. This time says "Nothing established contains this time." It does not say the time is free or available.

I. Schedule still has no Active Thread.

J. A fact that ends while the Tasks screen stays open leaves This time within about a minute of that end.
