# V0-001 — first usable task loop

Date: 2026-10-02.

The signed-in person can capture a Task, see open Tasks, and complete one. This is the first product surface. It is not NOW.

## Behavior

The home page has three visible states: checking the session, signed out, and signed in. Open tasks are not rendered until the session is known and the task load has finished.

Sign-in is email and password through Supabase Auth. The browser client persists the session and refreshes it. There is no registration form, no password reset, no roles, and no social login. Sign out is a secondary control.

Capture asks “What needs doing?” A title is required. Context, planned day, due date, and Must do are optional and start empty. Must do starts false. Saving uses `createTask`. A failed save leaves the draft in place and says that saving failed.

Open tasks are the rows returned by `loadOpenTasks`, in that creation order. The heading is “Open tasks.” The list does not rank, recommend, or decide what deserves attention.

Each open task shows its title. It shows Context, Planned, Due, and Must do only when those facts exist. Dates are civil-date labels. A past due date is shown as that date, without an overdue treatment.

Complete writes `completeTask` with the instant of the action, then removes the task from the open list. The row is not deleted. If the write fails, the task stays visible and the failure is stated in text.

## Auth note

The public Auth settings endpoint reported `disable_signup: false` for the dedicated project. The management API refused to change that setting. The application does not offer sign-up. `supabase/config.toml` now declares signup disabled for local configuration, and that file was not pushed, because a config push would also send other local auth settings such as the localhost site URL.

The hosted project still needs “Allow new users to sign up” turned off in the Supabase dashboard: Authentication → Sign In / Providers → Email.

## Exclusions

NOW, `rankNow`, Active Thread, Resume, Notes, Blocks, Commitments, Timeline, Today, Work schedule, cadence editing, recurrence, reminders, Pulse, Google Calendar, notifications, voice, a service worker, and AI are not part of this slice. No tables were added.

## Live validation

Before the interface work, the dedicated project had one confirmed user, four Contexts named Family, Financial, TeamLab, and Work, and no tasks.

A later check acted as that authenticated user inside a transaction that rolled back. It saw those four Contexts, inserted a task with Family, planned `2026-10-05`, due `2026-10-08`, and Must do set, then completed it. The open-task filter included it before completion and excluded it after. Planned and due stayed unchanged. The transaction ended with no task rows left.

The browser showed the sign-in screen, with no registration control. An empty submit stayed on that screen. An incorrect email and password kept the email and showed “That email and password did not match.” Open tasks were not shown. At a 390px-wide viewport the sign-in column fit without horizontal page overflow.

The browser was not signed in as the provisioned user. That password is not available to this session.

## Unresolved observations

- Public sign-up on the hosted project could not be turned off from this environment.
- The completion instant is the clock time of the completion action. It is not a user-edited timestamp.
- Reschedule, carry-forward, and whether completing should clear Must do remain product questions. Completion stores the instant and leaves the other fields as they were.
